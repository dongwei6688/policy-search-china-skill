# 公开面清扫：CHANGELOG / Release 正文 / wiki

用户指出「这些是不是都属于内部处理过程」时的标准动作。判据见 SKILL.md「公开 / 不公开的分界」。本文件只讲**怎么做干净**。

## 0. 先确认自己在发版源仓库

```bash
git -C <候选目录> describe --tags --abbrev=0      # 必须等于线上最新版本
```

不相等就是**镜像副本**——改下去等于白改，还要 `git checkout --` 还原，别污染它的工作树。发版源是发版脚本 `REPO` 常量指向的那个目录（镜像通常停在若干版之前）。

## 1. 三处公开面，各有各的改法

| 面 | 怎么改 |
|---|---|
| 仓库 `CHANGELOG.md` | 直接编辑 → 提交 → 推送（纯文档改动，不单独占版本号） |
| GitHub Release 正文 | **按数字 ID PATCH**，GitHub 不支持按 tag PATCH：`GET /repos/<owner>/<repo>/releases?per_page=100&page=N` 分页取全量（几十个版本时务必翻页），再 `PATCH /releases/{id}` |
| wiki `Changelog.md` | 克隆 wiki 仓库 → 改 → commit → push；**只换正文、保留原标题行**，不要顺手重排历史格式 |

发版源仓库里通常已有现成脚本（把 CHANGELOG 的版本正文逐版本同步到 Release 与 wiki），优先复用它而不是手搓；同步前先确认它的版本切分正则能覆盖**两种历史标题格式**：`## v2.55.1 (2026-10-16)` 与 `## [v2.8.0] — 2026-07-28`。只认前一种会漏掉一半旧版本（表现为 wiki 里旧条目还是脏的）。

## 2. 扫描：先把命中列全，再动手

对 CHANGELOG 正文逐行扫（按当前版本分组打印，便于判断影响面）：

- 内部字段与枚举：`date_source` / `date_evidence` / `backfill-*` / `verified-original` / `manual-verified` / `page-issued` / `doc-issued`
- 内部流程与队列：待补日期清单、交人工确认 / 复核、台账、核验统计（「N 条核验无误」「逐条依原文核验」）、过程拆分（「85 条 / 38 条」）
- 内部工具与实现：脚本名与函数名、`playwright` / `urllib` / `curl` / `WAF` / DOM、代码级描述（异常类名、`indent=1`、`import`、函数签名、常量名）
- 内部环境：缓存路径、`cache/*.json`、双空间同步、备份位置
- 内部角色/流程设计：指挥官 / 工人边界、阶段协议、审核检查点

## 3. 三档处理：改写 / 删除 / 结构归并

- **改写**（首选）：保留“使用者能看到什么”，去掉“我们怎么做的”。例：`被 WAF 拦截时 playwright 渲染提取全文（.pages_content）` → `页面直连受限时自动改用浏览器渲染提取全文`；`新增脚本：scripts/xxx.py（curl + playwright 双策略）` → **删除**（纯实现）；`遍历字典键触发 AttributeError 导致失败` → `多信源数据格式不一致导致的中断（现已兼容）`。
- **删除**：只描述内部实现、对使用者零信息的整条去掉。
- **结构归并**：删完会留下空小节（`### 重构` 下无条目）与空版本 → 去掉空小节；某版本一条不剩时补一行中性说明（如 `- 内部维护，对外无变化。`），别留空标题。

显式映射 + 正则兜底两段跑：先按精确行文本逐条替换（可审计、可回滚），再用内部词正则扫掉剩余的实现类条目行，最后归并空结构。改前把 `CHANGELOG.md` 备份到 `~/.hermes/backups/`。

## 4. 完整性核对（防删过头）

```bash
git show HEAD:CHANGELOG.md | grep -cE '^##\s*\[?v'   # 改前版本数
grep -cE '^##\s*\[?v' CHANGELOG.md                    # 改后必须相同
```

版本标题数必须一致；反扫内部词命中应为 0。

## 5. 复核必须独立

- **新克隆** wiki 后 grep（`raw.githubusercontent` 走 CDN 缓存，不能当判据）；Release 用单条接口 `GET /releases/tags/<v>` 取 body 再 grep。
- 抽查若干历史版本，不要只看最新一版。
- 结论报“三处各自命中 0 行 + 版本数一致”，别只报“已更新 N 处”。

## 6. 灰区怎么定性

字段名本身、仓库内脚本文件增删**可以写**（数据文件与脚本都在仓库里公开可见，调用方需要知道入口）；但不写实现内幕、运行环境、内部判据与内部队列。拿不准时按“这句话对使用者有没有用”判：有用→保留并中性化，没用→删。

## 7. 已知边界

- 只改当前文件不清历史：被删文字仍在 git 与 wiki 历史里；要清历史须重写并强推（见 SKILL.md 历史清理条）。
- 发版脚本的发行说明检查（内部词表告警）只是**告警不阻断**，写说明时仍要自己过一遍。
