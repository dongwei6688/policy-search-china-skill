# 口径裁定的落地与验收 + 历史数据回补

用户对政策库的裁定（“主题边界按内容判”“申报类剔除”“date 取发布日”…）不是改一句话，
而是一次**跨四处的口径变更 + 可验证的验收 + 存量处置**。本文是固定动作清单。

## 一、落地：改一处不算改完

同一条口径必须同时落在**四处**，缺一即视为未完成：

| 落点 | 具体位置 | 为什么不能省 |
|---|---|---|
| 门禁/流程代码 | `policy_theme_gate.py` / `policy_content_probe.py` / 入库脚本 | 只有代码改了，新的候选才真被拦/放行 |
| 每轮跑的规则文本 | 政策监控 cron 任务的 prompt | 指挥官读的是 prompt，不是代码；prompt 未同步 → 人仍按旧口径审核 |
| SKILL.md 口径段 | 主题门禁 / date / 发版等 bullet | 下次会话与分发包用户的唯一口径来源 |
| references/ | `policy-sources.md` 等 | 细节（词表、判据、历史实例）的落点 |

顺序：先改代码并跑通验证，再同步 prompt 与文档（顺序反了容易写成“文档先行”的假口径）。
改完在汇报里逐条报“四处分别落在哪个文件/任务”，不要只报“已落地”。

## 二、验收：三件套，缺一不算验过

1. **正向目标案例**：拿**触发本次裁定的那个真实文件**去跑（标题、URL 都取库内原值），确认判定翻转。
2. **反向回归（最容易被跳过的一步）**：主动构造**与新模式同词但语义不同**的标题，确认不被误伤。
   这是最有价值的一步——新增“申报/推荐/征集/遴选”类排除时，反例要选含“组织开展…**建设**工作的通知”，
   证明规则只咬“工作通知”不咬“组织开展类正式发文”。零反例的验证等于没验。
3. **影响面扫描**：把新词/新规则在**全库所有标题**上扫一遍，报告命中条数。
   期望值是 0（口径只作用于未来入库）。若不为 0，必须在汇报里逐条列出，并说明是否回溯。

## 三、存量：默认不动，例外要点名

- 用户裁定的字面选项若含“回溯清理存量”，而项目又有**存量不删除**的一贯铁律：
  按铁律执行**温和版**（新的不再入、存量保留），并在汇报里**显式说明这个收窄**，
  同时给出“若要真删”的路径（点名 → 备份 → 双空间同步 → 当日发版）。让用户一句话纠正，不要默默选一边。
- 应剔除但保留的存量要**留痕**：写进**内部台账**（`$HERMES_HOME/data/policy-search-china/internal/`，机器/人可读，
  逐条给日期 + 标题 + 规则名 + “保留不删”），**不进公开面**（公开面不得出现内部决策用语）。
- 台账的价值在于：日后用户点名清理时，清单现成、判据现成，不必重新推。

## 四、历史数据回补（以日期为例）

### 先量，再改（别按传闻下结论）

“历史条目日期都是入库日”这类传闻**先量再动手**：扫全库 `date_source` 分布，常常发现真值来源是
`candidate`/`url-day`，只是**缺标注**，而且多数日期本身是对的。先把“值错”与“缺标注”两类分开，
再决定改多少。汇报里要给这两个数（本次实测：错 100 / 对 74 / 待补 38）。

### 抽取顺序：离线优先

条目已存原文（`local_path` / `text_path`）→ **先离线抽**，只有抽不到才联网：

1. 网页存档 meta：`article:published_time` / `PubDate` / `publishdate` / `og:release_date` / `releasetime`；
2. 中文标签：`成文日期|印发日期|签发日期` 与 `发布日期|发布时间`，标签与日期之间允许空格/全角冒号/换行（**不要写死 `：`**）；
3. 公文惯例：独立一行的 `YYYY年M月D日`（取最后一次出现）；
4. 全无 → URL 反推（`tYYYYMMDD`、`/YYYY-MM/DD/`、`/YYYYMMDD/`）。

放宽第一版正则后离线覆盖率从 23/212 → 175/212，联网量从 189 降到 38。**先花十分钟改抽取规则，比多发一百个请求便宜。**

### 两条硬规则

- **证据优先于推断**：新值必须在**保存的原文里出现**才算数（附证据片段）；只有 meta/推断来源的一律挂起复核。
- **URL 反推不得覆盖原本就由 URL 派生的值**——零新信息（循环论证）。原值 = `url-day` 而新值也只能从 URL 得到时，保持不动。

### 写回纪律

`indent=1` 写回 + **双空间同步**（用户空间 → 系统空间）+ **逐文件 md5 校验**（本项目 16 个 cache 文件全要比）
+ 改动前整库备份到 `$HERMES_HOME/backups/policy-<变更名>-<时间戳>/`；改 `date` 属**数据修正**，
与“纯文档改动不单独发版”不同——**当日发版（patch）**，CHANGELOG 只写“修正 N 条条目日期”。

### `date_source` 取值语义（对账用）

`candidate`（候选自带）/ `url-day`·`url-month`（URL 反推）/ `page-metadata`（页面 meta）/
`backfill-original`（本次由原文证据更正）/ `verified-original`（日期与现值一致、经原文核验）/ `ingest-day`（入库日兜底）。
补标注（`verified-original`）**不改日期**，只让日后能一键分辨“核过”与“没核过”。

### 联网补取的纪律

派代理批量抓取时，输入输出都用**固定路径的 JSON**，并要求每条给 `evidence`（页面里含该日期的原文片段）、
`status`（ok / no_date / failed）。**明写“看不到就留空并标失败，不许编造”**——这份数据会直接写进公开库，
编造日期是不可接受的错误。降级顺序：换 UA 重试 → 政策库检索页/缓存 → 标 failed。

## 五、待裁定清单的汇整与结账

长期项目会不断积下“要不要收这类文件 / 口径怎么定”的悬而未决项（日常回补、内容层校验、日报里都会冒出）。
用户来问“要我裁定啥”时，不要零散复述，按下面的格式汇整：

- **只上升真正需要用户定的**：① 口径冲突或边界模糊 ② 会动到存量 ③ 要改代码行为 ④ 涉及公开发布面。
  其余按既有口径自行决定，并**单列一段“我自己处理、不用你裁定”**（带上理由），不要把无谓项塞进清单。
- **编号 + 依赖顺序**：`D1…Dn`，每条 = 一行问题 + 现状一句 + 选项 + **我的建议与理由**。
  有派生关系的把总纲排在前面（如“入库边界取宽/取窄”定了，后面的派生判据才好定）。
- **给出最小开工集**：标出“若只先定 3 条，建议先定哪几条”并说明理由（哪条决定松紧、哪条是真漏口）。
- **结论要结账**：用户裁定后，① 按本文二/三节落地四处并验收 ② 把对应的**待裁定事实改掉**
  （`fact_store change/end`，别让旧口径继续存在事实库里冒充现行）③ 把“口径已定”写进对应文档，
  不要只改记忆不改文档。
- **用户说“按你建议”时**：在执行前把实际采用的口径复述一句（建议往往比选项字面更窄——例如选项写“回溯清理存量”
  而建议是“存量保留”，实际执行后必须显式说明，否则用户以为存量被删了）。

## 六、汇报口径

- 每条裁定一行“落在哪四处 + 怎么验的（正例/反例/影响面三个数）”。
- 与建议不同的执行（如把“回溯清理”收窄为“存量保留”）**单列一段**请用户确认，别混在完成清单里。
- 分几批做完的事要说明**当前批次边界**与剩余待办，不要报“已完成”让用户以为全清了。
