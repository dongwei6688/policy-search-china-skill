# 原文实体性：索引有条目 ≠ 存到了正文

索引条目只放**元数据**（标题 / 日期 / 文号 / 来源链接 / 原文路径），正文在 `local_path` 指向的原文文件里。用户问「库里到底存了什么」时，要能拿出：条目 JSON + 原文文件 + 正文规模 + 双份 md5。

## 判定与体检

**单条判定**：原文文件存在 **且** 可提取正文 ≥ 500 字。
- HTML/HTM：去 `script/style`、去标签、反转义实体，数去空白后的字符数
- PDF：`pdftotext` 抽文字层；0 字 = 扫描版。**先找同名旁车文字层，再决定要不要重做 OCR**：扫描件旁边常已有 `<同名>.txt`（上一轮 OCR 的产物），先在同一目录找。确认它真是完整 OCR 的办法是**抽样复算**——挑 3～4 个不同位置的页现做一次 OCR，取每页较长的中文片段回到候选文本里检索，命中率高即可认定可用。几百页的扫描件重跑 OCR 动辄半小时以上，先查旁车文件能省掉整轮。

**全库体检（脚本化，五查）**：遍历所有条目的 `local_path`，**仓库 cache/ 与运行数据目录 cache/ 两处都查**，产出五类清单：
1. 正文过短（< 500 字）——多数是“只存到了页面框架”
2. 原文文件缺失——索引指向的文件不存在
3. 双份不一致——同名文件两处 md5 不同
4. **错误页**——正文里出现 `您访问的页面不存在` / `页面不存在或已删除` / `404 Not Found` / `页面未找到` / `Access Denied` 之一（一次全库字符串扫描即可，秒级，比逐条联网便宜得多）
5. **附件型**（最容易漏的一类）——条目 `local_path` 是网页、正文偏短（< 3000 字）、且该页含指向 `.pdf/.doc/.docx` 的链接

判据用**阈值分层**而不是单点阈值：正文 < 500 字几乎必是缺陷；500–3000 字区间混着“正文就在页面上”和“正文在附件里”两种，必须逐条比对（见下）才能定。只按 < 500 字体检会整批漏掉附件型条目——实测这批里有若干条 1200–2800 字的条目，附件里的正文是页面文本的 3–10 倍。

体检结果要按「主题内 / 主题外」分层输出：正文短 + 主题内 = 真缺陷必须修；正文短 + 主题外 = 存量清理候选（存量默认不动，需用户点名）。

## 三个高频成因与修法

### 1. 附件型页面（工信部、发改委、财政部、能源局、文旅部、生态环境部等）
正文是页面挂的官方附件（PDF / Word），HTML 抓取只能拿到发文机关、文号、成文日期、一两句通知话。症状：页面正文只有几百到两千余字，页面里含“附件”字样或直接给出 `href=….(pdf|doc|docx|wps|ofd)`。**不要用固定字数当判据**——几百字和两千多字都可能是附件型（例如“十五五”规划类页面常在 1,200–1,600 字，附件里却是上万字）。

**定性与修法（一条条走，不要整批盲改）**：
1. 抓页面，提取 `href` 里的附件直链（相对路径用 `urllib.parse.urljoin` 相对 `source_url` 解析），按 UA 下载到 `cache/<来源>/attachments/`
2. 抽附件文字：`.pdf` → `pdftotext -enc UTF-8`；`.doc` → `antiword -m UTF-8`；`.docx` → `unzip -p <f> word/document.xml` 后去标签
3. **算比值再决定**：附件文字 ≥ 2000 字 **且** 明显大于页面文本（经验线：> 2 倍）→ 附件才是正文，修；否则页面已含正文、附件只是附表/申报表/名单 → 保持原样并删掉刚下的附件，别留垃圾文件
4. 修法（字段口径）：`local_path` 改指附件文件、`format` 改成附件后缀、`attachment_url` 记附件直链、`text_path` 记抽出的文字层、`page_path` 保留原页面存档（页面本身也是证据），`indent=1` 写回
5. 附件是**扫描版**（`pdftotext` 0 字）：页数不多（≲ 8 页）时直接 OCR——`pdftoppm -r 200 -png` → `tesseract -l chi_sim` 逐页 → 拼成 `text_path`，条目加 `ocr: true`；页数多的大扫描件先找旁车文字层再决定是否重跑

> 修正的历史误判：早前把“附件型”的判据说成“HTML 抓下来 300–700 字”，导致一整批 1,200–2,800 字的附件型条目在体检里被判为“正常”。凡“页面文本明显短于同源同类文件”就该去看附件，而不是等它掉到几百字。

### 2. 原网址失效
抓下来的文件其实是 `404 Not Found` / `您访问的页面不存在`（个位数到几十字）。

修法：用站内搜索或官网栏目页找现址（同站点 `tYYYYMMDD_NNNNNNN` 编号相邻的页面常是同一文的另一版本）；换 `source_url` 并重抓；页面上有成文/发布日期元数据时同步修正 `date`，`date_source` 记 `page-metadata`。

判别纪律（先分清是哪一种，再动手）：① 用**条目里存的 URL 原样**重试一次——不要用手打或搜索结果里显示的写法代替，两者常差一个字符（`.htm` vs `.html`）从而得到假的 404；② 抽检同站同类 URL 是否正常（有些站惯例就是 `.htm`，本库大多数 `.htm` 链接都是好的）。多数“链接失效”其实是**抓取只拿到页面头部**，链接本身没错——按“链接坏了”处理会把对的链接改坏，也会把根因解释错。

### 3. 来源非官方
`source_url` 指向商业转载站时，一律回发文机关官网找原文替换——引用出处必须是官方发布源。

### 4. 全文从未公开发布的文件
有些文件（典型：中央深改委一类会议**审议通过**的意见/方案）**全文从未公开发布**，公开层面只有官方新闻与传达学习报道。此时站内怎么找都没有“原文页”，原链接会变成 404 页。

处置：**绝不拿新闻稿冒充政策原文**。把 `source_url` 改成发文/主管机关的官方报道页并抓存为 `local_path`，条目加 `note` 字段写明“全文未公开发布；本条正文为官方报道留档，非政策原文”，`date` 更正为审议通过日、`date_source` 记该依据，原 404 页留作 `page_path` 备查。汇报时明确说明这一条不是原文，别混在“已补齐正文”里。

## 可读文字层（`text_path`）

扫描版 PDF 条目在 `local_path`（原件）之外记一个 `text_path`（OCR 文字层），并标 `ocr: true`。两个作用：① 条目可检索；② **分发包据此排除原件 PDF**——原件的体积常比其余内容大一个数量级（单个 457 页扫描件就能占整包四分之三），包用户读文字层即可，原件仍留在仓库。

批量补完 `text_path` 后必须回读包内清单核对：PDF 数下降、索引条目数不变、被排除项确实不在包内。

## 修复三件套（改完必须做）

1. **双空间同步**：仓库 `cache/` 与运行区 `cache/` 写同一份内容，逐文件 md5 校验一致（索引 JSON 与原文文件都要）
2. **索引写回 `indent=1`**（与流水线一致；`indent=2` 会整文件重排产生海量 diff 噪声）；改前备份索引 JSON
3. **当日发版**（cache 变更必发），Release notes 写明「补取了哪几条正文 / 换了哪些来源」

替换旧原文时：旧文件**移出仓库**留档（备份目录在仓库外），不要就地删——旧文件可能就是将来排查“当时存到了什么”的唯一凭据。

## 批量修复的安全纪律（三类回来咬人的坑）

- **改条目一律用标题全等匹配，不用子串**：按子串匹配批量改字段，会命中标题相近的另一条并在多个 JSON 里各改一份（例：拿一个四字关键词去匹配，误改了标题里含同一词的另一条，散布在两份索引里）。改完**打印改前/改后字段**；一旦误改，用 `git diff -U0 -- cache/*.json` 读出原值，再按标题全等逐条恢复，恢复后回读复核两条各自的取值——不要 `git checkout` 整个 JSON 回滚，会把同一批里的其它修复一起丢掉。
- **“跳过”分支不要删除已登记的文件**：批量脚本里对不合格附件做清理时，删除的目标路径若与**前一步已登记**的附件路径算法相同，会把刚登记好的原件删掉（文字层还在，但 `local_path` 悬空）。清理只针对**本次下载且未登记**的文件，或在删除前先查该路径是否已被任何条目引用。
- **双空间同步要覆盖新增文件，不只索引**：批量新增 `local_path` / `text_path` / `page_path` 后，把这些文件也复制到运行数据目录（运行区 `local_path` 不得悬空），然后**双向核验**：仓库侧引用的文件都存在、运行区引用的文件都存在（悬空数应为 0）。只同步 JSON 会出现“索引齐全、原文打不开”。

## 验证：与官网逐段比对

修复后用同一套抓取逻辑再取一次官网页面，把「库内正文段落集合」与「官网段落集合」比对，重合度应为 **100%**（段落按去空白后 > 20 字的行切分）。这一步同时验证完整性与“存的是官网原文而非别的版本”。

## 交付呈现（用户要看原文时）

- **在聊天里贴 Markdown 正文**（可分段），不要发 `.htm/.html` 附件——飞书等客户端打不开 HTML 附件；纯文本 `.txt` 可以发。
- 顺序：先说清“库里存的是什么结构”（索引元数据 + 原文文件 + 正文规模 + 双份一致），再给正文，让用户能自己判断。
- 汇报体检结果时给**修复前/后计数**，让改善可核。
